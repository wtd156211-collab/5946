# 生产数据脱敏与还原

要把生产库的一份导出拿给外部做压测和演示，里面有客户姓名、手机号、邮箱、银行卡号、身份证号和订单金额，法务不让原样给出去。以前是拿脚本随机替换的，出了两个事：同一个人在两个文件里变成了两个人，对不上；还有同事拿回文件想反查是哪个客户，一点头绪都没有，因为替换是随机的，原值根本没留。这次要做成能来回的。

几件事必须同时成立。脱敏之后的字段还得是合法的：手机号、卡号校验位、身份证校验位都要过，邮箱还得是邮箱的样子，日期还得是真实存在的日期，下游有格式校验，过不了就白干。同一个原值，不管出现在哪一列、哪一批，映射出来的结果必须一样；不同原值不能撞到同一个结果，不然对账的时候会莫名其妙多出重复。反过来，拿着密钥要把整份数据还原成原样，一个字节都不能差，所以会保存一份还原要用的东西，要写清楚它存什么、放在哪、怎么保证它本身不泄露原值。另外几条约束也得保住：本来唯一的列还得唯一，日期先后不能乱，金额的量级要差不多、不能本来几百块变成几百万，两个文件之间的引用关系不能断。量上，线上那份导出两千多万行，得边读边处理，内存不能跟着行数涨。换一个密钥，同一个原值必须映射成另一个结果，这条要能被验证，别写成固定偏移那种。

仓库现在只有这份说明、samples/ 下两份导出和一份列定义，代码从零写。实现只用标准库，测试用 unittest。

## 数据与列定义

samples/ 下有三份材料：`export-batch-1.csv` 与 `export-batch-2.csv` 是同一批客户在两个批次里的订单导出，客户在两份文件里有重叠，可以用来验证「同一原值跨文件、跨批次映射一致」和「引用关系不断」；`columns.json` 是列定义，每列给出 `name`、`type` 和 `mask` 规则，`type` 决定脱敏后目标值要满足的合法性要求。

`mask` 的取值：

| mask | 含义 |
|---|---|
| `keep` | 原样保留，不参与脱敏（引用键与订单号） |
| `valid-fake` | 换成同类型、仍然合法的假值：`cn_name` 中文姓名、`cn_mobile` 11 位手机号、`email` 邮箱、`pan` 过 Luhn 校验的卡号、`cn_id` 过校验位且出生日期真实存在的 18 位身份证 |
| `shift` | 日期整体位移，必须保持先后顺序 |
| `jitter` | 金额小幅扰动，保持量级（`decimal_cny`，两位小数） |

两份样例里的手机号、卡号、身份证都是按上面规则生成的合法值，可以直接拿来检查校验位。

## 用法

```bash
# 1. 生成密钥（32 字节随机数，base64 保存，权限 600）
python3 -m datamask init-key --out key.b64

# 2. 逐份脱敏（多批文件共用同一把密钥、同一份清单，跨批映射自然一致）
python3 -m datamask mask --columns samples/columns.json --key-file key.b64 \
    --manifest manifest.jsonl --in samples/export-batch-1.csv --out masked-1.csv

# 3. 还原（密钥 + 清单，输出与原始文件逐字节一致，并自动做 SHA-256 校验）
python3 -m datamask restore --columns samples/columns.json --key-file key.b64 \
    --manifest manifest.jsonl --in masked-1.csv --out restored-1.csv
```

只用标准库；测试：`python3 -m unittest discover -s tests`。

## 列规则的实际处理方式

映射全部由「主密钥 + 列类型 + 原值」决定，不含列名和行号，所以同一原值
无论出现在哪一列、哪一份文件、哪一批，结果都相同；脱敏和还原都是逐行流式
处理，内存不随行数增长（缓存有 20 万条上限，超出后只算不存）。

| mask | 处理方式 |
|---|---|
| `keep` | 原样保留（`customer_id`、`order_id`），引用关系不断 |
| `valid-fake` / `cn_name` | 长度不变，把姓名看作 CJK 字符（U+4E00–U+9FFF）编码的整数，做一次 FPE |
| `valid-fake` / `cn_mobile` | `1[3-9]xxxxxxxxx` 编码为 `[0, 7*10^9)` 的整数做 FPE，结果仍是合法手机号 |
| `valid-fake` / `email` | local 部分和每个域名标签内的 `[A-Za-z0-9]` 游程分别做定长 FPE（顶级标签只用字母表），其余字符不动，结果仍是合法邮箱 |
| `valid-fake` / `pan` | 除末位外的数字做 FPE，末位按 Luhn 重算，卡号必过校验 |
| `valid-fake` / `cn_id` | 地址码（10^6）、出生日期（1900-01-01～2024-12-31 的天数区间）、顺序码（10^3）分别 FPE，校验位按 GB 规则重算，出生日期必为真实日期 |
| `shift` / `date` | 整体平移密钥派生的固定天数（±365 天内、恒非零），先后顺序不变 |
| `jitter` / `decimal_cny` | 以分为单位，在 `10^(d-2)` 大小的分块内做 FPE（d 为分值的位数）：扰动幅度约 ±10% 以内、数量级严格不变、两位小数、单射可逆 |

值域外的异常值（如含生僻字符的姓名、超过两位小数的金额）走兜底：生成确定性的
合法假值，同时把原值加密写入还原清单（见下），还原时优先查清单。

## 映射是怎么算出来的

核心是 `datamask/fpe.py` 里的格式保留加密：Feistel 网络（6 轮，轮函数为
SHA-256）+ cycle-walking，对任意模数 M 在 `[0, M)` 上构成一个**置换**——

- **确定性**：同一 (密钥, 类型, 原值) 恒得同一结果，跨列、跨批一致；
- **单射**：置换保证不同原值不会撞到同一结果，唯一列脱敏后仍唯一；
- **可逆**：持密钥可逆推，所以还原不依赖逐值对照表；
- **密钥相关**：主密钥经 HMAC-SHA256 派生出各用途子密钥（`cn_mobile`、
  `pan`、`date-shift`……），换一把密钥得到完全不同的置换。这不是固定偏移：
  测试 `test_key_change_changes_every_type` 对全部七种类型验证换密钥后映射必变。

日期位移量、金额分块置换同样从主密钥派生，全部变换都可凭密钥精确逆推。

## 还原清单：格式、存放与保密性

清单是 JSONL 文件（每行一条 JSON 记录），脱敏时追加写入，多批文件共用一份：

- `header`：格式版本、数据集名、**密钥指纹**（SHA-256 前 16 位，还原时校验
  是不是原来那把密钥，拿错钥匙直接报错而不是还出乱码）、列定义哈希、创建时间；
- `file`：每个脱敏输出文件的行数、**原始文件与脱敏文件的 SHA-256**。还原后
  自动比对，逐字节一致才报「校验通过」；
- `fallback`：值域外异常值的加密原值，格式为
  `{"kind":"fallback","type":...,"masked":...,"original_enc":base64,"tag":...}`。

**为什么不泄露原值**：`fallback` 里的原值用密钥派生的流密码加密（HMAC-SHA256
计数器模式产生密钥流，逐字节异或），并带 HMAC 完整性标签；`file` 记录只存整
文件哈希，不含任何字段值。没有密钥，清单里读不出任何原始字段——测试
`test_manifest_does_not_leak_originals` 会拿全部原始值在清单里逐个搜一遍。

**存放位置**：与脱敏输出放在一起（默认 `manifest.jsonl`），但它必须和密钥
**分开保管**——清单不含密钥，密钥文件（`key.b64`）不应进入交付给外部的任何
目录。常规数据（全部落在值域内）不会产生 `fallback` 记录，此时清单只有
header 和 file 校验信息，还原完全靠密钥逆推。

## 已知边界

- `cn_name` 支持 2–4 个 CJK 字符，超出走清单兜底；
- `cn_id` 仅支持 18 位，出生日期需在 1900–2024 之间，超出走清单兜底；
- 金额超过两位小数、无法解析的日期等同样走清单兜底；
- 兜底映射是确定性伪随机，不保证单射（异常值本身极少，且原值已入清单，还原不受影响）。
